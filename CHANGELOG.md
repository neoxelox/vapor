# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) with pre-GA policy details defined in `docs/operations/release-process.md`.

## [Unreleased]

### Added

- Tier S, the soak: `./scripts/soak.sh` (`tools/soak`, `vapor-soak`, never shipped) puts the real `vapor` and `vapord` in a sandbox and runs hours of seeded file churn on both the local root and the cloud root (creates, overwrites, same-size edits, appends, renames, moves, deletes, subtree removals, directories, mode flips; loads `mixed`, `trickle`, `coding`, `bulk`, `large`; modes two-way, pull-only, push-only) in phases separated by quiescence. After every phase a model of what must survive checks both trees: nothing lost, nothing invented (every byte traces back to a workload write), both trees converged, one-way reverts honoured, contested payloads of the conflict phase both surviving. Faults: SIGKILL between operations and mid-transfer with a restart, SIGSTOP/SIGCONT, pause and resume, a config reload, the cloud root renamed away for a phase, the cloud volume filled to the last block (on a throwaway disk image), and a throttle walk. The driver writes `soak-status.json` every few seconds for an agent to watch, `ops.jsonl` continuously, `model.json` after every phase, and `soak-report.json` with every verdict, fault, violation, health maximum, and the SLO checks; the first violation freezes the run with the daemon up and the sandbox intact. `soak.yml` runs a nightly matrix of cells on the macOS runner; `scripts/perf.sh` runs one release-profile cell as the Tier 2 gate and asserts the SLO checks on its report, replacing the placeholder that re-ran Tier 1 with a time budget. New `vapor-soak` skill; process doc `docs/development/soak-testing.md`.
- Decisions: when an irreversible action rests on evidence that can be read two ways, the daemon parks the question instead of guessing or stopping. A decision is durable (`pending_decisions` in the profile state DB, schema v6), scoped to one path, one batch, or one profile, and holds only the intents inside that scope in a new `held` queue state; everything else keeps syncing and the daemon is never paused for it. `vapor decisions list|show|resolve <id> --choose <key>` read and answer them with or without a running daemon (the app drives the same command with `--json`); the daemon applies the answer on its next tick or at its next start. `vapor status` counts them (`decisions_pending`, total and per profile), `vapor diagnostics` shows held rows as `Held` with the decision as the blocker, and the timeline records the question and the outcome. Design: `data-flow.md` §Decisions, including the short list of conditions that stop a whole profile.
- The mass-deletion guard now watches both directions and asks instead of pausing. A burst of deletions arriving from this device or from the cloud is judged as a whole (the deletions still queued count with the ones applied inside the window), so a batch that reaches `massDeleteThreshold` (now 1000) or the new `massDeleteRatioPercent` of the synced tree (25%, never fewer than 10 files) is held whole behind one `mass-deletion` decision before its first member lands on the other side; a deletion that is a no-op never counts. `apply` releases the batch, `discard` drops it and restores every path from the side that still has the file. The old behaviour paused the whole daemon on 200 local deletions until `vapor resume`, and counted cloud-side deletions not at all. Covered by guard, executor and runtime tests and e2e S31 and S40; the soak driver answers the decisions its subtree removals provoke.
- `VAPOR_THROTTLE_INPUTS=file:<path>`: the daemon re-reads a JSON document (`{"inputs": <ThrottleInputs>, "idle_seconds": N}`) on every throttle sample and idle probe, falling back to the neutral defaults while the file is missing or half-written, so a driver can walk the real daemon through every throttle state. `vapor doctor` names the source.
- The end-to-end harness is a Rust dev crate (`tools/e2e`, `vapor-e2e`) that `./scripts/e2e.sh` wraps, replacing the 942-line bash script. Every scenario now runs in its own sandbox and ends with two shared checks the old script never had: a tree oracle that compares the local root and the cloud root file by file (paths, sizes, content hashes, executable bits, ignored and internal names excluded), and log hygiene over every daemon the scenario started (no `ERROR` line, no warning outside the routine set plus what the scenario declared, no failed intent). `--only Sxx` runs one scenario, `--list` prints the catalog with each scenario's needs, `--json` writes a machine-readable report (every job uploads it as a CI artifact), `--daemon vapord` drives the shipped daemon binary, `--sandbox-stop` stops and removes manual sandboxes, and `./scripts/clean.sh` stops sandbox daemons before deleting their homes. Scenarios declare what they need from the host (native watcher, Unix, FIFOs, POSIX modes, launchd, a disk image) and skip by name elsewhere, so the harness runs on every CI OS job. Fifteen scenarios are new: SIGKILL in the middle of an upload and of a download with restart recovery, file and directory renames and a cross-subtree move, `rm -rf` of a tree followed by a file of the same name, nested directory trees in both directions, offline local and cloud deletes (pinning today's restore-on-restart rule), push-only end to end, two profiles in one daemon, the mass-deletion guard tripping and re-arming, the state DB deleted before a restart, a case-only name collision through a case-sensitive disk image, the cloud root vanishing and returning mid-run, the `vapord` binary itself, and a push-only same-size divergence. Five of them document known gaps found on their first run and stay in the suite as expected failures until the engine catches up (a known-gap scenario that starts passing makes the run red until its marker is removed). The old script's silent-failure bug is gone: an unguarded failure used to exit through the cleanup trap and delete the sandbox with no diagnostics; every non-zero exit now preserves the sandbox and prints status, diagnostics, queue rows, and log tails for every daemon.

- The Mac app shows what the daemon is doing. The Dashboard and menu-bar status used to be a static "Idle" that only ever flipped to "Error" on a config or lifecycle failure, so a paused, throttled, syncing, or failing daemon still read as idle. The 30-second health tick now also reads `vapor status --json` when the daemon is running, and a pure mapping turns the daemon's run state, throttle state, queue depth and failed count into the surface state (idle, syncing, throttled, suspended, paused, stopped, error) with the daemon's throttle reason underneath. A restart-required configuration change from the daemon shows as a notice with a "Restart sync" button on the Dashboard and in Settings, and "Restart sync" is always available from the menu bar; both run `vapor service restart` through the lifecycle queue. The mapping and the tick are covered by logic tests; the rendering is verified by hand.
- Live configuration reload. The daemon composed its pipeline from `vapor.json` once and never looked again, so every `vapor config set` and every Settings change needed a daemon restart that nothing offered, while three documents described reload semantics that did not exist. The daemon now stats the file once per second; the resource ceilings, idle boost, mass-delete guard, ignore toggles and rules, and the timeline length apply on the tick that notices the change (the budget adopts new bounds without restarting an in-progress boost ramp, per the ceiling-transition rules in `data-flow.md`). The keys that reshape the pipeline (`localSyncDirectory`, `cloudSyncDirectory`, `provider`, `syncMode`, `profiles`, `deviceId`) are reported in `vapor status` as `config_restart_required` with the command to run, `vapor config set` prints which class a key falls in, and the Settings copy in the Mac app no longer says rules wait for the next launch. A file that stops loading is reported once and ignored, so a typo never drops a running daemon to defaults. Covered by unit tests, a multi-profile integration test, and e2e S22.

### Fixed

- A cloud edit that kept the byte count while the daemon was not running now reaches this device. The sync index recorded only the local mtime, so the startup reconcile compared the cloud side by size alone and a same-size rewrite in the cloud folder stayed invisible (the filesystem provider's changes cursor is process-local, so the feed never reported it either). The provider now reports the remote object's mtime with every completed transfer, the index records it, and the walk applies the rsync quick check to both sides. The planner also stopped trusting the op-id tag alone as proof that the remote is unchanged (an in-place write keeps the tag), and when the local copy still equals the last synced hash it downloads the remote change instead of manufacturing a conflict copy of an unchanged file. Found by a six-minute soak with faults; covered by executor and runtime tests and e2e S41.
- An upload whose local file vanished between planning and the transfer (a save followed by a rename or delete) no longer fails permanently with an ERROR line and a `failed_intents` row. The watcher has already reported the path's new state, so the transfer completes as a no-op. Found by the first soak run with faults; covered by an executor test.
- Deleting a remote directory that holds only Vapor's own leftovers (a staging temp from a crash mid-upload, the side-file of a file already gone) now succeeds instead of retrying "Directory not empty" forever. Those files are invisible to listings, so the engine could never delete them itself; user content is still never reaped. Found by a soak that crashed the daemon mid-transfer and then removed the folder; covered by a provider test.
- Renaming or moving a local folder now reaches the cloud. A directory rename reached the daemon as one `Removed` and one `Created` event with nothing for the files inside, so the new folder's contents were never uploaded, and the delete of the old folder was non-recursive and retried forever on "Directory not empty". A directory that appears is now walked and its files reported as the watcher events a copy would have produced (ignored names pruned, oversized subtrees deferred to a reconcile marker), and a directory delete expands into one guarded per-file delete, deepest first, with the directory itself last, so a file the cloud changed since the last sync is still preserved rather than deleted with its folder. Found by e2e S25; covered by S25, executor and runtime tests.
- Replacing a deleted folder with a file of the same name no longer leaves a permanently failed intent. The filesystem provider's changes feed emitted "optimistic" create events for paths under the new file (a `NotADirectory` stat), which became downloads that failed with "cannot verify sync-root containment". `NotADirectory` now reads as a removal, since an ancestor that is a file proves the object is gone. Found by e2e S26.
- The reconcile walk no longer takes an equal-size pair it has no index row for as converged. After a lost state DB, or on the first sync of two pre-populated roots, the index stayed empty and a later same-size offline edit of those files went unnoticed; in push-only, a same-size cloud edit present at first start was never overwritten. Index-less pairs are now verified once through the upload planner, which hashes them, converges silently on identical content, and records the row. Found by e2e S32 and S37.
- Two cloud objects whose names differ only by case no longer rewrite each other on a case-insensitive local filesystem. The second download landed on the first one's file as a keep-both apply, and the following upload overwrote the cloud object it came from. The reconcile walk, the changes-feed mapping, and the download apply now refuse to map a remote name that would alias a differently-cased local file: both cloud objects and the local file stay untouched, a warning is logged once per name, and a `collision` timeline event names both paths. Materializing the second object as a conflict copy is tracked in `docs/tasks/core.md`. Found by e2e S33; covered by S38.
- A local change reported moments before SIGTERM is no longer lost from memory. Events still inside their debounce window lived only in the process, and a clean shutdown took them with it until the next startup reconcile found the file. The runtime now stabilizes every pending event at shutdown and writes the intents to the durable queue first; the shutdown log line reports `intents_flushed`. Found by e2e S08's tree oracle; covered by S39 and a runtime test.
- Two routine transitions no longer log as warnings: the clean shutdown message and the filesystem provider's changes cursor not surviving a restart (its cursor is process-local) are INFO; a cursor that expires mid-run stays a warning because it means a feed gap. The e2e harness now fails a healthy run on any warning.

### Changed

- `Provider::rename` and the `supports_server_side_rename` capability are gone from the provider contract. No engine path called them: a rename intent has always been planned as an upload of the new path plus a delete of the old one, so the two providers implemented a method nothing used and the contract suite tested a promise the product did not keep. Move detection that turns FSEvents rename pairs into a server-side move is tracked as future work; until it lands, renaming a large file re-uploads it.
- Per-profile `resourceLimits` and `idleBoost` overrides are now partial. They used to deserialize into the full group struct, so a profile that set only `cpuPercent` silently pulled `memoryPercent` and `bandwidthPercent` down to the compiled defaults, and the four idle-boost fields the daemon never read (`minIdleSeconds`, `headroomCpuPercent`, `rampUpSeconds`, `rampDownSeconds`) were accepted and ignored. Every override field is optional; the daemon merges each named field toward caution (ceilings, headroom and the down-ramp can only shrink, the idle requirement and the up-ramp can only grow, `enabled: false` wins) and leaves unnamed fields at the top-level value. The `profiles` row in the README states the rule.
- `vapor config set` takes JSON for the structured keys (`profiles`, `resourceLimits`, `idleBoost`, `safeguards`) and validates it against the type the daemon loads. It used to store any string verbatim, so `config set resourceLimits '{"cpuPercent":5}'` wrote a JSON *string* that the daemon logged as invalid at startup and replaced with defaults, silently ignoring the user's ceiling. Non-JSON or wrong-shaped values are rejected with the expected shape. `vapor config get` renders the compiled default for a key that has never been set instead of an empty line; `deviceId` stays empty until the daemon derives it.
- `vapor service --help` documents `start`, `stop`, `restart` and `status`, and `--system` carries its own description instead of borrowing `--user`'s.
- The inert test provider is constructed through `inert_stub_provider()`; the old `default_provider()` name and its doc comment claimed it was the runtime default, which stopped being true when the real filesystem provider became selectable.
- `CONTRIBUTING.md` and `SECURITY.md` spell the command `vapor support-bundle`, which is what the CLI accepts.
- Mac app cleanups: the unused English `SyncSurfaceState.detail` strings and `AppShellState.statusLine` are gone along with the two tests that only checked they were non-empty; the duplicate `VaporConstants.Providers` folded into `Provider`; the `@available(macOS 13)` guards that could never fail on a macOS 26 deployment target are removed; and a CLI launch that fails to spawn now closes its pipe write ends so the drain closures finish immediately instead of whenever the pipes deinit.
- Routine throttle transitions log at INFO; only entering `Suspended` is a WARNING. A healthy e2e run used to end with six warnings that were all "Updated throttle state".
- Every `vapor.json` writer (the CLI, the daemon's IPC path, the lifecycle store, device-id persistence) goes through one helper in `core/shared` that stages a 0600 temp file under a 0700 parent and renames it into place. Two of the four writers used a plain `fs::write` (0644) and one skipped the cross-process lock's staging discipline. The lifecycle side-file uses a per-writer temp name too, so the app's health tick and a user's `vapor service` command cannot race on one staging path.
- `vapor diagnostics` rows for intents that are mid-execution carry their real attempt count and last error instead of zero and an empty string, and the queued rows list in lease order (priority, then availability) so the display matches what the executor will drain next.
- A remote-origin tombstone no longer wins over a local file whose mtime cannot be read; an unreadable mtime cannot prove the file predates the deletion, so the file stays.
- A two-way file/directory type mismatch found by the reconcile walk is pushed to the activity timeline once per pass with what to do about it, instead of only repeating a log warning.
- An upload whose preflight finds the remote gone re-dispatches with an `Absent` precondition, so a concurrent re-creation is caught as a race rather than overwritten.
- The streaming hasher reuses its 64 KiB buffer across slices instead of allocating one per step.
- `scripts/version.sh` checks the lockfile entry of every workspace member, derived from the manifest, instead of a hand-kept list of three crates. The Rust wrapper scripts dropped a bootstrap-era fallback for a missing workspace manifest.
- `scripts/cli/{build,test}.sh` are gone; they duplicated `cargo` commands the workspace-wide scripts already run.
- Doc comments and READMEs caught up: the IPC crate no longer calls its envelopes "JSON-RPC 2.0-style", the providers README describes the shipped providers and the three contract fixtures, the daemon README describes forward migrations and no longer claims `proptest` is in use, and three sentences left dangling by an earlier task-id purge read whole again. The IPC oversized-frame test now asserts the `PayloadTooLarge` error frame and the EOF that follows it instead of reading and discarding.

### Fixed

- Google Drive entries whose name contains `/` are logged at WARNING when the provider skips them during enumeration. They cannot be represented as a sync path, and a silent skip left a file that never syncs with no trace of why.
- A download range that answers with an empty body now fails the step as transient instead of reporting zero progress forever. The worker loop refunded the whole grant and stepped again at once, so a misbehaving endpoint or proxy could spin a worker at full speed without the intent ever failing into retry backoff. The Google Drive session rejects the empty body itself, and the transfer loop independently fails any session that reports eight zero-byte steps in a row.
- Offline same-size edits now sync. The reconcile walk compared files by size only and the macOS watcher starts from "now", so an edit made while the daemon was not running that kept the byte count (a config tweak, a source edit) was invisible to both paths and never uploaded. The walk now applies the rsync quick check: equal sizes still diverge when the sync index shows the local mtime moved since the last transfer, and the upload planner hashes the file and converges silently when the bytes are in fact unchanged. The same quick check in the executor compared a nanosecond mtime against the millisecond value the index stores, so it never matched and every "unchanged?" question fell through to a full hash; both sites now compare at the millisecond. Covered by a runtime integration test and e2e S20.
- The changes poll, the reconcile walk's directory listings and the cloud-root retry no longer run on the tick thread. Moving the executor's calls onto worker threads had left these three behind, so with Google Drive every poll (as often as every 5 seconds) and every `enumerate` froze all profiles for one round trip. Each now starts on its own thread and is harvested on a later tick; the walk resumes at the directory whose listing landed. Tests keep the inline mode, so nothing about their determinism changed.
- A daemon whose every profile is misconfigured (invalid provider, overlapping roots, an unopenable state DB, Google Drive without client credentials) used to exit at once, which sent it straight into launchd restarts and the crash-loop pause, and `vapor status` could never show the reason. It now stays up on the idle cadence serving status with the per-profile `suspended_reason`, logs once that it is serving status only, and exits only when a profile fails at runtime. Covered by a unit test and e2e S21.
- A downloaded file that displaces a local copy no longer hashes the displaced bytes on the tick thread in the common case. The keep-both apply compares the pre-rename size and mtime against the sync index first, and hashes only when the sizes leave room for the bytes to be equal, so a multi-gigabyte apply of an untouched local file costs a stat instead of a full read while other profiles wait.
- A provider call that panics on a worker thread no longer wedges its intent forever. The worker died with the permit and the in-flight slot leaked, the execution sat in its stage renewing its lease on every sweep, and nothing ever reported it. The worker now catches the panic, stays alive, and reports it; the executor fails the intent permanently with the panic message so it shows up in `failed_intents` instead of hanging. Release builds abort on panic and never reach this path.
- `vapor doctor` run from the app bundle (`Contents/Helpers/vapor`) reported `vapord_binary` as FAIL and exited 1, because its resolver only looked next to the CLI and on `PATH` while `vapor service install` also knew the bundled `Contents/MacOS/vapord` layout. Both commands now share one resolver (sibling, bundle, `PATH`, in that order) and the row names where the daemon was found. The report also gained `--json` (`{"checks": [...], "worst_status": ...}`), a `secret_store` row saying whether tokens persist on this OS, a `throttle_inputs` row saying where the throttle signals come from, and a `host_` prefix on the LaunchAgent row since it reads host state even when `VAPOR_DIR` points at a sandbox. The e2e harness asserts the JSON shape.
- Release CI concurrency. The reusable `lint`, `test` and `build` workflows used the caller's `github.workflow` and `github.ref` in their concurrency group, so a release run resolved every called workflow to the release job's own group, and the cancel expression evaluated to `true` on a tag ref. Each reusable workflow now carries its own name in the group and never cancels runs on `main` or on a tag.

### Added

- Real throttle inputs on macOS. The native metrics sampler was a static placeholder, so the throttle ladder only ever reacted to the active-coding heuristic and idle boost could never engage because the idle notifier reported zero idle time. The daemon now reads system and daemon CPU load, power source, thermal state, Low Power Mode, resident and physical memory, and keyboard/pointer presence from the host once per throttle interval, and the idle notifier reads the HID idle clock (falling back to always-idle when there is no window-server session, as under SSH or a CI agent). Input within the last 30 seconds marks the user as active, which holds the throttle at `Throttled`. `vapor status` reports the daemon's real memory share instead of a hard-coded zero, and the memory ceiling compares resident size against the configured share of device memory in addition to the cache entry budget. Linux and Windows keep static defaults and the daemon logs a warning saying so. `VAPOR_THROTTLE_INPUTS=static` pins any daemon to the neutral inputs; `scripts/e2e.sh` sets it so a run is not shaped by whoever is typing on the machine.
- macOS secret store. `vapor auth login` now writes the token to the login keychain instead of process memory, so the daemon can read it and Google Drive sync survives the CLI exiting. Each secret is one generic-password item under the `sh.arn.vapor` service, created with an access list that names `vapor` and `vapord` so the daemon reads CLI-stored tokens without a keychain prompt. The in-memory fake and the keychain store run the same contract test; Linux and Windows keep explicit `Unsupported` stubs and the CLI warns when it has to fall back to memory. Operational notes, including the one-time prompt after rebuilding an unsigned development binary, are in `docs/operations/provider-auth-operations.md`.

### Tooling / CI

- `./scripts/test.sh` runs `cargo test --no-fail-fast`, so a failing crate no longer hides the results of the crates tested after it. The Windows verbatim-path bug above stayed masked for one CI round for exactly that reason: `vapor-daemon` failed first and `vapor-shared` never ran.
- Deleted GitHub's default `documentation` and `enhancement` labels. They duplicated `docs` and `feat`, and `.github/release.yml` only recognises the latter, so a PR labelled with a default would silently drop out of the release notes.
- `main` is now protected by a repository ruleset. It requires a pull request with one approval (stale approvals dismissed on push, and one extra approval for pull requests authored by the Copilot coding agent), requires all nine Tier 1 checks (`lint`, `test`, `build` × `macos-latest` / `ubuntu-latest` / `windows-latest`, each bound to the GitHub Actions app) on a branch that is up to date with `main`, and blocks force pushes and deletion. Until now `main` had no protection at all, although `AGENTS.md` §9.5 already described Tier 1 as a required check. The repository-admin role can bypass the ruleset: with a single maintainer that is how pull requests get merged, since nobody else can approve them, and it keeps the documented release flow — a direct `git push origin main --follow-tags` of the release-prep commit — working; GitHub records every bypass. Live configuration, rationale, and the command to recreate it: `docs/ci/required-checks.md`.
- GitHub Actions are now allowlisted in repository settings: GitHub-owned actions plus explicit patterns for the two third-party actions the workflows use (`maxim-lobanov/setup-xcode`, `actions-rust-lang/setup-rust-toolchain`) and for `Swatinem/rust-cache`, which no workflow references but `setup-rust-toolchain` nests inside its composite `action.yml` — the policy is evaluated for nested references too, even when the nested step is unreachable, and the first run under the allowlist failed on exactly that; Marketplace "verified creators" are not admitted as a class. SHA pinning already guarantees the referenced actions run the reviewed code; the allowlist stops anyone from introducing a fifth action through a workflow edit, including inside the release job that holds the signing certificate. The order of operations this imposes — allow the pattern *before* a workflow references the action, otherwise the step is refused and the change cannot be tested — is now a rule in `AGENTS.md` §7.1, with the current list and commands in `docs/ci/overview.md`.
- Secret scanning and push protection are enabled on the repository. Scanning covers the full history and every branch and opens a private alert for anything shaped like a known credential (the earlier publication audit found none, so this is protection against a future slip); push protection rejects such a push before it lands, with a logged bypass for test fixtures. Private vulnerability reporting is enabled too, so the preferred channel named in `SECURITY.md` actually exists. `CONTRIBUTING.md` explains what to do when a push is blocked.
- Workflows triggered by pull requests from forks now wait for maintainer approval for every external contributor, not only first-time ones. Fork runs already get a read-only token and no secrets, but they still execute the PR's code on the runner, including `./scripts/e2e.sh --full`, which installs a real LaunchAgent; a public repository should not run that on a drive-by PR without a human looking first. Recorded in `docs/ci/overview.md`.
- CI macOS jobs run on `macos-latest` instead of the pinned `macos-26` label. Both resolve to the same macOS 26 arm64 image today, so this changes nothing now; it keeps the macOS leg on GitHub's latest stable image per `AGENTS.md` §8.2 as the alias rolls forward. The required-check names changed with it (`lint (macos-latest)` and so on), so the ruleset was created against the new names. `docs/ci/{overview,required-checks}.md` also catch up with the action versions pinned in the previous change set.
- The optional pre-commit hook no longer runs `clean.sh` (full-repo review): it builds incrementally (`lint → test → build`) so commits are fast, and — the genuine fix — it no longer wipes `.vapor`/`dist`, which previously destroyed a preserved or running e2e sandbox on every commit. The from-scratch, empty-cache guarantee is owned by CI (fresh checkout on every PR); test execution is never cached, so a failing test can't slip through incrementally.
- Shared external dependencies are pinned once in a root `[workspace.dependencies]` table and inherited via `{ workspace = true }` across all seven crate manifests (full-repo review), so a version bump no longer risks a missed hand-duplicated copy producing conflicting `=` pins that break workspace resolution.
- Release & CI pipeline fixes (full-repo review):
  - The tag-reachability preflight uses a full `git fetch` (not `--depth=1`), so a valid release tag is no longer deterministically rejected once `main` advances past it.
  - Re-running the release workflow no longer demotes an already-published release back to draft (it only re-applies `--draft` to a still-draft release) and reconciles the prerelease flag explicitly.
  - The release job's cargo/SPM caches are release-scoped with no prefix restore-keys, so signed/notarized artifacts cannot link objects restored from another job's cache; the PR workflows key their caches per workflow so they stop fighting over one shared key.
  - Packaged-output validation also asserts `Contents/Helpers/vapor` (the third mandated executable).
  - PR workflows cancel superseded runs via a concurrency group (main pushes and release-invoked runs are never cancelled; the release-tag case and the per-workflow group names were corrected in the next review round, see "Fixed" above).
- Every third-party GitHub Action is pinned to a full commit SHA with the release it resolves to kept in a trailing comment (`actions/checkout` v7.0.1, `actions/cache` v5.1.0, `maxim-lobanov/setup-xcode` v1.7.0, `actions-rust-lang/setup-rust-toolchain` v1.17.0). Version tags are mutable, and `setup-xcode` / `setup-rust-toolchain` both run in the release job several steps before the Developer ID certificate is imported into the runner keychain — a repointed tag could have captured that certificate and its password. Pinning freezes the exact behaviour those tags resolve to today; picking up future releases is now a deliberate bump.
- Updated the lagging actions as part of that pass; each was verified input-compatible by diffing `action.yml` across the upgrade, so no call site changed:
  - `actions/checkout` v6.1.0 → v7.0.1. The two `action.yml` files are byte-identical (same inputs, same defaults including `persist-credentials`, same `node24` runtime), so the major bump is internal: an ESM migration plus a hardening change that blocks checking out a fork PR under `pull_request_target` / `workflow_run`. Neither trigger is used here, and v7.0.1's fix to skip that check when `ref` is left at its default applies to every call site in this repo, none of which set `ref`.
  - `maxim-lobanov/setup-xcode` v1.6.0 → v1.7.0. The sole interface change is the action runtime moving from `node20` to `node24`, which keeps the Xcode setup step ahead of the Actions node20 deprecation. `xcode-version` remains the only input.
  - `actions-rust-lang/setup-rust-toolchain` v1.9.0 → v1.17.0, which fixes two things directly on Vapor's code path. Because the repo has a `rust-toolchain.toml` and passes no `toolchain` input, the action takes its toolchain-file branch: that branch replaced the implicit `rustup show` with the explicit `rustup show active-toolchain || rustup toolchain install`, the supported form now that rustup is removing implicit installation. Separately, the "install rustup if needed" step no longer skips Windows and resolves `CARGO_HOME` from `$USERPROFILE`, which matters for the `windows-latest` portability jobs. The `rustflags` default is unchanged at `-D warnings`, so build strictness is identical, and every input added since v1.9.0 is optional and inert here. ### Fixed (providers & auth)

- Provider & OAuth fixes (full-repo review):
  - `vapor auth login gdrive` now percent-decodes the authorization code before the token exchange, so real Google logins no longer fail with `invalid_grant`; the loopback listener validates a CSPRNG `state`, loops on accept with per-connection read timeouts and an overall deadline (a stray/speculative socket can no longer kill the login), and renders a proper page on denied consent.
  - The native HTTP transport uses explicit connect/read/write timeouts (a black-holed connection can no longer wedge the synchronous provider stack forever) and errors instead of silently truncating a response body past the size cap.
  - The filesystem reference provider deletes a directory with `remove_dir` (fails on non-empty) instead of `remove_dir_all`, so a delete intent can never recursively destroy remote children the engine never observed.
  - The filesystem reference provider's upload session now verifies a `HashEquals` precondition by reading the old remote copy in budgeted slices (instead of one unbounded hash inside a single `step()`), so overwriting a multi-GB file no longer stalls the tick loop past throttle transitions or shutdown; it re-checks the target's `(size, mtime)` immediately before the rename to narrow the check-then-act window, and commits `Absent` uploads with an atomic no-clobber create (hard-link) so a concurrent writer that lands the target mid-transfer is refused (keep-both) rather than silently overwritten. A residual sub-stat TOCTOU on a shared network mount remains a documented limitation of the reference provider.
  - Google Drive provider: Google-native objects (Docs/Sheets/shortcuts) are excluded from enumerate/stat/changes (no more phantom 0-byte files); multipart uploads use a random collision-checked boundary; resumable uploads honor the 308 `Range` committed offset; downloads verify the full body arrived on a 200; and 403 `dailyLimitExceeded`/rate-limit reasons back off instead of dropping the intent (`storageQuotaExceeded` surfaces distinctly).
  - PKCE code verifiers and the OAuth `state` are generated from the OS CSPRNG; `HttpRequest` and `StoredTokens` `Debug` impls redact tokens.
  - The Google Drive changes feed (which is Drive-wide) now remembers file ids it has resolved to be outside the sync root in a TTL-bounded negative cache, so a busy out-of-scope file (a colleague's doc edited every minute) is rejected with zero requests on subsequent polls instead of re-walking its whole parent chain each cycle — cutting battery/network/API-quota churn and rate-limit-storm risk. The memory expires so a file moved into scope is still picked up, and is dropped immediately once a file resolves in-scope.
  - Google Drive transfer sessions now share the provider's one `TokenManager` (an `Arc` clone per request) instead of constructing a fresh one with an empty cache on every chunk PUT / range GET — no more SecretStore read + token-parse on the hot transfer path — and the session request path inherits the one-shot `401` force-refresh-and-resend, so a token that expires mid-upload resends that one chunk instead of failing the whole multi-gigabyte intent terminally.
  - Google Drive rename/move convergence and overwrite safety: duplicate file names in a folder now resolve deterministically (lowest id) instead of an arbitrary match; a path->id cache hit is validated against the file's current name/parent (and folder invalidations evict the whole subtree) so an edit can no longer be written into a file that was renamed or moved out of the sync root; `path_for_changed_file` derives the current path from the change's own name/parents (emitting a delete-at-old + create-at-new for a remote rename) instead of returning a stale cached path that never converged; and the `HashEquals` upload precondition is re-verified with a single re-stat immediately before the committing request (multipart PATCH/POST and the final resumable chunk), shrinking the check-then-act window from the whole transfer to one round-trip so a concurrent remote edit surfaces as keep-both instead of a silent last-write-wins overwrite.

- `vapor conflicts` safety (full-repo review): resolving with `--keep copy` only deletes the canonical file for the Windows destination-exists collision it was written for (error kind `AlreadyExists`), not on any rename failure — so a read-only remount or I/O error no longer destroys the canonical version inside a failing path. `vapor conflicts list` now records unreadable subdirectories in a new `skippedDirectories` field (surfaced in text and `--json`), so a conflict copy under a `chmod 000` directory is reported instead of invisibly orphaned behind "No unresolved conflicts."

### Performance

- Transfer concurrency is core-aware (field testing): the IdleDrain tier derives from the machine's available parallelism (half the cores, clamped 4–8 per direction, read tokens scaling alongside) and the provider-job worker cap follows it, so a 16-core desktop drains twice as wide as before while small machines keep the classic caps — and the throttle ladder still collapses everything the moment the user is active.
- Storm-deferred reconciles release early when the device is already idle and the burst has been quiet for 5s (field testing), instead of always waiting out the full 30s deferral — a repo clone appears in the cloud folder seconds after it finishes, while an ongoing storm (or an active user) still defers fully.
- Provider I/O moved off the runtime tick thread onto a provider-job worker pool (full-repo review, final wave): remote stats/hash probes, `begin_upload`/`begin_download`, transfer-session steps, and remote deletes now run on lazily-spawned workers while the tick loop dispatches jobs and harvests outcomes. Network round-trip time no longer stalls fs-event draining, debounce, remote polling, or IPC status, and the upload/download concurrency caps buy genuinely parallel transfers instead of time-slicing one thread. Throttle discipline is preserved: workers re-check the gates and the bandwidth bucket between steps and hand a held session back at its checkpoint under `Suspended` or an empty bucket.
- Zero-cost pipeline stage transitions chain within one tick (full-repo review, final wave): a freshly leased intent plans in its lease tick, a granted hash permit reads its first chunk immediately, and a finished hash dispatches its transfer in the same pass — removing ~4 ticks (~1s at the busy cadence) of fixed latency from every small-file sync.
- Durable lease order is now priority-aware (schema v5, full-repo review, final wave): reconcile control intents lease first, fresh file intents rank by their debounce class (key config before code before lockfile noise), and reconcile-walk backlog leases last — a whole-scope reconcile of tens of thousands of files can no longer make a file the user just edited wait behind the entire backlog. A fresh edit coalescing onto a queued backlog row promotes its rank.
- A path blocked by its own in-flight transfer no longer breaks the whole admission batch (full-repo review, final wave): per-path serialization requeues just that intent and the rest of the leased batch keeps starting, so one long transfer cannot pin unrelated work behind it in lockstep.
- A fully idle daemon no longer runs per-profile SQLite queries on every 1 Hz wakeup (full-repo review, final wave): the status snapshot republishes only when work happened, a control request arrived, a profile's state changed, or a 10s heartbeat elapses, and the auto-tuner gathers its queue-depth signal only when its ~90s cycle is actually due.
- The auto-tuner judges step-increase regressions on drain rate (completed intents per cycle) instead of absolute queue depth (full-repo review, final wave): during a sustained ingest burst — exactly when a deeper queue needs throughput — an increase that improved completion rate now sticks instead of being rolled back every cycle.
- The storm detector interns each event path as one 64-bit fingerprint and iterates ancestors in place (full-repo review, final wave), dropping the per-event `PathBuf` clone per directory level and deferring the unique-path window scan until the count could actually trip the threshold.
- Idle-boost recovers from a momentary headroom blip (full-repo review): the resource budget re-checks its gates while ramping down and, once headroom returns, resumes climbing from the current level instead of riding the full down-ramp and then a fresh up-ramp — so a 1-second background CPU spike no longer costs ~40s of reduced ceilings.
- The bandwidth shaper now refunds the unspent portion of a transfer-step grant (full-repo review): per-step chunk-size alignment slack and failed (zero-byte) steps are returned to the shared token bucket (clamped to the one-second cap), so sustained upload throughput no longer systematically undershoots the configured rate and a retry storm cannot burn the shared budget.
- Sync-pipeline latency & device-impact improvements (full-repo review):
  - The remote poller keeps draining while a page is full instead of waiting a full cadence between pages, so a large remote burst (thousands of files) enqueues in seconds rather than minutes.
  - The reconcile walk scales its per-tick directory budget up under IdleDrain and is bounded by a wall-clock slice deadline checked between directories, so a large tree converges fast on the filesystem provider while a slow network provider's `enumerate` can no longer hold the tick thread for a whole chunk.
  - Echo-suppression no longer hashes an entire large file inline on the tick thread (which also bypassed the Suspended-stops-hashing invariant): files above the hash-step size correlate by op-id tag instead.
  - Ignore-file events inside excluded directories no longer trigger wasted full-tree filter rebuilds.
  - Office documents, PDFs, and images get a ~1.5s debounce window (a new document class) instead of the 4s `Other` window, so the files users care about most reach the cloud ~2.5s sooner.

### Fixed

- Cloud-side deletions (and edits) of files that Vapor itself uploaded now propagate reliably (field testing): the upload's atomic no-clobber commit used a hard-link + unlink pair, which left macOS FSEvents' file-level tracking bound to the deleted temp name — the uploaded file was invisible to the changes feed for its entire lifetime, so an external `rm` in the cloud folder produced zero watcher events and never reached the local side (reproduced live, deterministic). The commit is now a true atomic no-clobber rename (`renamex_np(RENAME_EXCL)` on macOS, `renameat2(RENAME_NOREPLACE)` on Linux, link-based fallback only where no such API exists), keeping both the concurrent-writer guard and watcher visibility; a new e2e scenario (S19) drives the exact failing sequence through the live feed with no reconcile. The remote poller and changes feed also gained debug-level logs for every received, suppressed, and enqueued change so a lost event is diagnosable from the daemon log.
- Deleting the cloud sync root out from under a running daemon now self-heals instead of looping (field testing): scope failures caused by a vanished root classify as a dedicated `CloudRootUnavailable` condition, the daemon blocks admission and surfaces the Error state, the periodic ensure loop recreates the root, and a post-recovery whole-scope reconcile re-uploads local content into it (the two-way walk only deletes locally behind a remote-origin tombstone, so an empty recreated root can never mirror its emptiness back). Previously the reconcile walk retried a permanent "escapes the cloud sync root" error every second, forever.
- Overlapping `localSyncDirectory` / `cloudSyncDirectory` on a filesystem-backed profile now suspend the profile with an actionable reason (field testing): equal or nested roots (checked through symlinks) would feed the engine its own provider writes — self-sustaining churn, and potentially destructive under a pull-only strict mirror. The suspended profile never even creates the misconfigured cloud root.
- `cloudSyncDirectory` resolves like a local path when the provider is filesystem-backed (field testing): `~/x` expands against the home directory and relative values anchor to the working directory, instead of being blindly prefixed into the unusable literal `/~/x` ("Read-only file system"). Real cloud providers keep root-relative remote-path semantics.
- POSIX file modes carry over through filesystem-backed sync (field testing): uploads and downloads apply the source file's permissions to the staged payload before the atomic rename, so a `0755` script no longer arrives as `0644`. Mode-only changes still do not propagate (documented), and providers without a native mode concept (Google Drive) do not preserve modes.
- The macOS app shows the real provider instead of the hardcoded "Filesystem (stub)" placeholder (field testing): the label now derives from the configured `provider` value (`Filesystem`, `Google Drive`), and the stale constant is gone.
- The daemon's local filesystem watch now consumes the `core/platform` `FsWatcher` trait (full-repo review, final wave): the duplicated (and already drifted) OS-event mapping in `core/daemon` is gone, directional renames and paired-rename splitting live in the one platform mapping shared with the filesystem provider's changes feed, watcher backend errors are forwarded instead of silently dropped, and `vapor-daemon` no longer depends on `notify` directly.
- The macOS app surfaces a blocked login item instead of silently reporting "Start at login" as ON (full-repo review, final wave): when macOS defers or refuses the registration (user disabled it in System Settings, or MDM policy), the settings surfaces show a hint with a one-click path to System Settings › General › Login Items.
- The IPC client's deadline now also bounds the connect phase (full-repo review, final wave): on a host where a wedged daemon accept loop fills the kernel backlog (AF_UNIX connect blocks indefinitely on Linux), `vapor status` and friends time out cleanly instead of hanging forever.
- `VAPOR_DIR` resolution canonicalizes through the filesystem (full-repo review, final wave): symlinked and real spellings of the same directory converge on one canonical path, so a daemon launched under one spelling and a CLI under another can no longer hash different IPC socket relocations and fail to find each other.
- Every `vapor.json` writer now shares one cross-process advisory file-lock and a per-writer temp name (full-repo review): the daemon's IPC config path, the CLI's `vapor config`, and the auto-launch setting store no longer interleave read-modify-write cycles, so two concurrent writers (e.g. the app toggling auto-launch while a `vapor config` command runs) can no longer have the last rename silently revert the other's key — and a second writer's rename can no longer fail spuriously by consuming a shared staging file.
- Filesystem provider & sync-index robustness (full-repo review):
  - A transient (non-`NotFound`) stat failure while normalizing a filesystem watch event now emits the change optimistically (the engine re-stats before acting) and logs it, instead of silently dropping it from the feed until the next reconcile.
  - Orphaned `.vapor-tmp-*` staging files (upload/download stages interrupted by an unclean crash) are reaped once older than a conservative age as the provider's enumeration and the reconcile walk pass over them, so they can no longer accumulate hidden in the user's folder across repeated crashes; in-flight (young) temps are left untouched. The op-id side-file's own staging temp now lives inside the reserved internal namespace so a crash mid-write cannot leak a `*.tmp` file that a user-edited ignore rule might sync.
  - After a download, the sync index records the *remote* object's op-id (whichever device wrote it) rather than this device's download id, so a later upload of that path correlates by op-id instead of falling back to a full-remote-read hash comparison.
  - Non-UTF-8 file names (unrepresentable in the sync path model) are now logged when skipped by enumeration, the watch feed, and the reconcile walk, so a file that silently never syncs is diagnosable (macOS enforces UTF-8, so this is rare).
- The Google Drive changes feed treats a parsable response that advances no cursor (neither `nextPageToken` nor `newStartPageToken`) as a transient error instead of durably re-polling the identical page forever.
- Remote-path and op-id-tag safety (full-repo review):
  - A `\` in a remote path is no longer treated as a separator (that translation belongs only at the Windows-native boundary): a macOS/Linux file legally named `foo\bar.txt` is one object, refused rather than silently remapped into a nested `foo` → `bar.txt` that duplicates and re-uploads on every edit. `RemotePath::join` now rejects a segment that itself contains a separator, so a Drive object legally named `a/b` cannot expand into two folder levels.
  - The op-id side-file tag store never overwrites or deletes a real user file that merely shares the reserved `.vapor-meta.json` suffix: writes/relocations refuse to clobber a path occupied by non-metadata content, and removal only deletes a path that actually parses as our metadata.
- More bidirectional-sync data-loss fixes (full-repo review):
  - A process-wide `VAPOR_LOCAL/CLOUD_SYNC_DIRECTORY` env var no longer silently overrides a profile's explicit per-profile directory (which collapsed every profile onto one root — catastrophic for a one-way mirror profile). The env layer now applies only to fields a profile did not set, with a loud warning when overridden.
  - A local `read_dir`/`stat` failure during reconcile (EPERM/EACCES/EMFILE/EIO) no longer reads as "no local entries": the directory is deferred instead of driving strict-mirror remote deletes of content that still exists locally.
  - The daemon's own upload echoes are suppressed by a durable second-line correlator (persisted sync-index op-id / content hash), so they are no longer re-downloaded (or turned into phantom conflicts) once the ~30s live echo record expires under the 60s Throttled poll cadence or a Suspended pause.
  - Remote-sourced intents are enqueued with the change's observed time (not the poll time), and a two-way `ApplyRemoteDelete` re-stats the remote first — so a stale `Removed` from a lagging feed can no longer delete a freshly re-uploaded/edited local file.
- Daemon run-state & pause correctness (full-repo review):
  - Recovering an unavailable cloud root no longer silently clears an active pause (an explicit `vapor pause` or the mass-deletion guard): it only clears the cloud-root `Error` state, so queued mass deletions cannot replicate without the human review the pause exists to force.
  - A paused daemon no longer polls the remote changes feed (matching the documented pause semantics — no more provider API traffic while the user believes sync is fully paused).
  - `vapor resume` while the cloud root is unavailable now reports the blocking `Error` state (with the real reason) instead of a misleading `Running`.
  - Timeline events are attributed to the real profile id in multi-profile daemons instead of always `default`.
  - The activity timeline capacity is restored to its configured value after a transient memory-pressure squeeze instead of staying shrunk until restart.
- Ignore-rule filtering (full-repo review):
  - A bare directory pattern (`target`, `/build`) now excludes the directory's whole subtree, matching git semantics — a Rust repo's `target` entry no longer left every build artifact watched, hashed, and uploaded.
  - `should_ignore` now matches through a single compiled glob-set automaton instead of a per-event linear scan of every rule, so a monorepo with thousands of ignore lines no longer runs millions of regex evaluations per event burst on the fs-watch callback thread.
  - Ignore files inside a user-excluded directory are no longer read (mirroring git), so a vendored `.gitignore`/`.vaporignore` negation can no longer re-include content the user opted out of, and startup discovery no longer descends huge excluded trees.
- Multi-profile daemon blast-radius containment (full-repo review):
  - A profile with an invalid/misspelled provider is now suspended at composition (surfaced in status as `Error`) instead of falling back to a live no-op stub — which, for a pull-only profile, would have let the startup reconcile classify the whole local root as local-only and strict-mirror-delete it.
  - A suspended or panicking profile now reclaims the shared-workgate permits its in-flight transfers and running reconcile held, so healthy profiles are no longer starved of upload/hash/reconcile concurrency for the process lifetime.
  - The daemon no longer exits when a suspended profile coexists with a healthy profile that hits a single transient tick error: the "all profiles failed" exit is now based on durable per-slot state, not a per-tick report.
  - A per-profile startup failure (DB open, watcher/root, reconcile scheduling) degrades to skipping/suspending that profile instead of aborting the whole daemon; the auto-tuner also skips suspended slots (better tuning signal, no reads of a half-mutated post-panic runtime).
- Durable state DB robustness (full-repo review):
  - Corruption recovery now quarantines the DB only on genuine corruption (`SQLITE_CORRUPT` / `SQLITE_NOTADB`); transient failures (disk full, I/O error, busy lock, permission) surface as ordinary startup errors instead of destroying every pending intent, tombstone, and sync-index baseline.
  - The in-run stale-lease sweep no longer reclaims work a live execution still holds: the runtime renews the leases of in-flight transfers (and a running reconcile) before each sweep, so a large upload or a Suspended stall past the 15-minute lease timeout is not duplicated; recovered leases also keep their retry history.
  - A server `Retry-After` is clamped to a one-hour ceiling with checked time arithmetic, so a bogus/absurd header can no longer overflow (panic) the daemon or persist a multi-year global rate-limit slowdown.
  - New indexes back the coalesced-enqueue dedup lookup and the diagnostics list ordering (no more full table scans on a deep queue every ingest flush / status publish).
  - `failed_intents` now has a retention sweep (age window + newest-N cap) at startup, so a single auth outage that finalizes thousands of rows can no longer grow the DB without bound.
  - The v3→v4 migration restores the AUTOINCREMENT high-water mark, so a migrated-with-empty-queue database can no longer hand out an id that collides with an existing `failed_intents` primary key (which previously wedged the intent in a recurring tick-error loop).
  - `schedule_retry` now writes the requeue and the durable rate-limit slowdown marker in one transaction (a crash between them no longer drops the slowdown), and the retry-budget cap is enforced (an exhausted transient intent finalizes as permanent instead of looping through the stale sweep forever).
- Bidirectional-sync data-loss and correctness fixes in the staged executor (full-repo review):
  - A local delete no longer destroys a concurrent remote modification: in two-way mode a delete only propagates when the remote still matches the last sync (op-id or content hash); a diverged remote is preserved and pulled back via a Download instead of deleted.
  - A remote directory deletion no longer wipes unsynced local files: two-way `ApplyRemoteDelete` on a directory now walks the subtree, removing only synced-and-unchanged files and preserving (and re-uploading) everything else, deleting the directory only once it is empty.
  - Divergence, deletion, and echo-suppression checks now hash local files in the *provider's* algorithm (MD5 for Google Drive) instead of a hard-coded SHA-256, so MD5 providers no longer manufacture endless spurious keep-both copies or refuse every remote deletion.
  - Applying a remote change can no longer escape the local sync root through a symlinked parent directory: download-apply and remote-delete-apply verify sync-root containment non-lexically and refuse a target whose parent resolves outside the root.
  - Download-apply keep-both no longer has a check-then-act window: the existing local file is renamed aside first and the divergence decision runs on the exact displaced bytes, so a local edit that lands during a download is never silently overwritten.
  - A crash between a completed upload and the durable index write no longer replays as a phantom keep-both conflict on both replicas: the op-id-mismatch path defers to the upload gate, which converges byte-identical content silently.
  - Conflict follow-ups are enqueued crash-safely (the canonical-restore Download before the local rename), the redundant re-Download on download-side conflicts is gone, and a mid-transfer local edit no longer pairs a post-edit mtime with the as-uploaded hash (the mtime fast-path is disabled when the file changed during transfer).
- The `vapor` CLI no longer panics with "failed printing to stdout: Broken pipe" when a downstream pipe reader exits early (`vapor logs | head -1`, `vapor status --json | grep -q ...`): default SIGPIPE handling is restored on Unix so the CLI behaves like standard tools in pipelines. The Tier E2E harness also stopped closing pipes on the CLI mid-write (capture-then-match), removing a timing-dependent CI failure.

### Fixed

- Special files (FIFOs, sockets, device nodes) can no longer wedge the sync queue. An upload intent for a FIFO passed the planner's directory/symlink guards and then sat in the durable queue forever as a permanently-`WaitingForHash` row (hashing a FIFO blocks until a writer appears). The planner and the reconcile walk now treat anything that is not a regular file or directory as explicitly inert — the intent completes as convergence and no remote object is created. The engine's file-only contract (folders as implicit containers, symlinks/special files invisible, hard links as independent files) is now documented in `data-flow.md §Directory and symlink semantics`.
- Uploading over an externally-written cloud file no longer manufactures a spurious keep-both conflict. The upload planner treated any remote op-id mismatch as concurrent divergence, but the tag is absent on every externally-written file (which Vapor may have already synced *from*) — so the everyday round-trip "external cloud edit → download → local edit → upload" produced a conflict copy every time, and could even revert a conflict the user had just resolved (the S15 e2e flake). The planner now verifies the remote content hash against the sync index before declaring divergence: an equal hash is a safe guarded overwrite; only a genuinely changed remote keeps both.
- A local edit made shortly after a download can no longer be swallowed by echo suppression. Local write echoes correlated primarily by the file's op-id tag, but the tag survives later writes — so for the echo record's whole TTL after a download-apply, genuine user edits to that file matched the stale tag and were suppressed as the daemon's own write (and a same-size edit would stay unsynced even past reconcile's size-based fast path). Write-echo correlation now requires the file's current content to match what the daemon wrote (size-gated hash check); the op-id tag alone is never sufficient.
- Local deletions now reliably propagate to the cloud. Intent classification trusted the *last* fs-watch fragment for a path, but real backends (FSEvents especially) coalesce and split per-path flags, so an unlinked file's final fragment is frequently a write-kind — the deletion became an upload plan that no-op'd as "vanished before upload" and the remote copy was never removed (the same misclassification also under-counted the mass-deletion guard). Deletion is now decided by ground truth: when a stabilized burst carries a removal or rename and the path is gone at stabilization time, the intent is a delete regardless of fragment order; a removed-then-recreated file correctly uploads the survivor instead of deleting the remote copy. The synthetic-event integration tests always injected clean `Removed` events, which is why only a real-binary run (Tier E2E S15/S16) could catch this. Regression-locked at unit, integration, and e2e level.
- Ignore rules now apply symmetrically. They were only enforced on the local fs-watch ingest path, so an ignored name appearing on the cloud side (a `.DS_Store` written into a filesystem-provider mirror, a `node_modules/` tree uploaded by another device) was pulled down by the remote changes feed and the reconcile walk — and a divergent local counterpart the watcher rightly never uploaded then manufactured a spurious keep-both `~conflict-` copy. The runtime's shared path filter (one instance per canonical root, shared with the watcher so ignore-file reloads propagate everywhere, including across profiles watching the same root) is now consulted by the reconcile comparison walk (both sides of every directory pair; ignored directories are not descended into) and by the remote-change mapping (dropped changes are counted as `ignored_changes`). An ignored name never syncs in either direction. Found by project-owner manual testing; regression-locked by unit, integration, and Tier E2E (S14) coverage.
- The filesystem provider no longer advertises a remote-changes feed on hosts whose native fs-watcher is still a stub (Linux until Wave 13, Windows until Wave 12): polling would fail transiently forever. The capability is now host-honest and the engine falls back to reconcile enumeration, per the provider contract.
- Linux metadata tags now actually persist: user-space extended attributes require the `user.` namespace prefix on Linux, which the native `FilesystemCapabilities` tag store was not applying — every xattr write failed `EOPNOTSUPP` and op-id tagging silently fell back to side-files. The portable tag name is unchanged; the prefix is applied at the Linux storage boundary. Removing a tag from a filesystem that cannot hold tags is now also treated as convergence (nothing to remove) instead of an error.
- A reconcile whose comparison walk had already finished could yield "for the next safe slice" instead of completing — forever, when every tick exhausted the slice budget — holding the startup barrier up and starving every intent queued behind it. A finished walk now completes regardless of the slice checkpoint (there is nothing left to slice); a lost reconcile controller aborts defensively instead of wedging the leased intent. Found by the new Tier E2E bidirectional scenario; regression-locked by `requested_reconcile_with_flush_boost_downloads_external_cloud_file_and_drains`.
- An interrupted lease batch can no longer strand intents. `lease_ready_batch` marks every returned row leased up front, but the admission loop could `break` (blocked permit, startup barrier) after processing only part of the batch — the remainder sat invisibly leased until the stale-lease sweep. The unprocessed remainder is now handed back to pending in the same tick.
- `vapor pause` now actually pauses work. The IPC pause request previously flipped the `RunState` snapshot string while the runtime kept releasing, leasing, and executing intents — `vapor status` said `Paused` and nothing changed. The tick loop now gates work admission on the run state: ingest, debounce, and the durable flush keep capturing intent state (so nothing is ever lost while paused) and in-flight executions run to completion, but no new work is released or leased until `vapor resume`. Regression test `paused_daemon_stops_admitting_new_work_and_resume_restores_it` asserts zero leases across paused ticks, continued intent capture, and full backlog admission on resume.
- The Rust and Swift crash-loop guards no longer disagree on the backoff schedule. The Rust port gave the first crash a free restart while the Swift original (and the LaunchAgent policy doc) backed off immediately — so the effective schedule depended on which surface observed the crash, and the parity test file the Rust module cited did not exist. The canonical schedule is now `crash 1 → restart immediately, crash 2 → 2s, crash 3 → 4s, crash 4 → 8s, paused on the 5th` (default policy); the Swift `CrashLoopGuard` is aligned to it, `docs/operations/macos/launchagent-policy.md` documents it, and the new `core/lifecycle/tests/crash_loop_parity.rs` + mirrored Swift test lock both sides to the same contract. The policy doc also stops claiming durable crash counters and an app health tick that were never built — both are marked planned.
- Persisted configuration now actually reaches the daemon. `vapor config set localSyncDirectory …` (and every other key except `autoLaunch`) used to be write-only: the daemon resolved its sync scope and ignore rules from environment variables alone, and `vapor service install` wrote a LaunchAgent with an empty environment. A new tolerant loader in `core/shared::config` reads `vapor.json` at daemon startup with the canonical precedence `VAPOR_*` env var → `vapor.json` → compiled default (`sync_directories::resolve_with_config`, `EventPathFilterOptions::from_environment_and_config`). Both LaunchAgent writers — the macOS app and `vapor service install` — now emit the same policy-shaped plist (environment: `VAPOR_DIR` + `VAPOR_ENV` pass-through only; stdout/stderr under `<vapor_dir>/logs/`), so the two surfaces stop silently clobbering each other's daemon configuration; the app's previous workaround of shoving eight config values through plist environment variables is gone.
- Exactly one daemon per `vapor_dir` is now enforced. A second `vapord` (or `vapor run`) used to race the first on the durable queue and silently steal its IPC socket (`bind_listener` unlinks a pre-existing socket file); `vapor run`'s doc comment claimed WAL-lock detection that never existed. A new `core/daemon::singleton::SingletonLock` takes an OS advisory file lock on `<vapor_dir>/vapord.lock` before anything binds or opens; the second instance exits with `daemon already running`. The lock releases automatically on process exit, including crashes.
- Throttle escalations no longer wait out the hysteresis dwell window. The min-dwell logic held the previous state for *any* transition, so a machine that entered Low Power Mode or critical thermal pressure while dwelling in `Light` kept full-speed caps for up to 5 s. Dwell now applies only to relaxations (toward `IdleDrain`); moves to a more conservative state apply on the next sample. Regression test `escalation_to_more_conservative_state_bypasses_the_dwell_window` covers both directions.
- Events dropped at the bounded fs-ingest boundary are repaired instead of silently lost. The recorder counted overflow drops for diagnostics but nothing consumed the counter, so changes arriving faster than the runtime drained were lost until the next restart. The drain path now schedules a deferred whole-scope reconcile (new `StormReason::IngestOverflow`) covering the unknown lost changes, preserving the "never lose intent state" guarantee under callback-vs-runtime backpressure.
- A checkpoint-paused reconcile no longer multiplies durable intents. Pausing preserved the intent both as a requeued durable row and as a pending scheduler entry, and the next flush inserted a brand-new durable row for the scheduler copy — one duplicate per pause, each later running a redundant whole-subtree reconcile (up to ~4 rows/second during the startup barrier with an active user). The scheduler flush now coalesces per `(path, kind)` against already-pending durable rows inside a single transaction, which also collapses N per-intent fsyncs into one and deduplicates repeated edits to the same path. Regression test `checkpoint_paused_reconcile_does_not_duplicate_durable_rows` holds the queue depth at 1 across repeated pause cycles.
- One inconsistent durable row can no longer kill the daemon. A `complete_leased` / `requeue_leased` that matched zero rows returned `InvalidIntentState`, which propagated out of the tick and made `run_forever` exit the process (and with `KeepAlive=false`, launchd never restarts it). Row-level inconsistencies are now logged and the affected intent dropped (at-least-once semantics make this safe); the loop tolerates up to 5 consecutive tick failures before treating the error as structural and exiting.
- Storm detection can no longer compact the entire sync scope on a busy-but-healthy workload. Per-directory thresholds were counted in every ancestor window up to the watch root, so ~600 events spread across unrelated subdirectories within 2 s tripped the root window and collapsed all pending work into one whole-scope deferred reconcile. The per-directory thresholds now apply strictly below the root; the root compacts only via the dedicated (much higher) global pending threshold. Continued churn is also bounded: a deferred reconcile can be pushed back at most `DEFERRED_RECONCILE_MAX_DELAY_MILLIS` (10 min) past first detection, so a never-quiet subtree still converges.
- Ignore-rule edits now apply without a daemon restart. The compiled `.gitignore` / `.vaporignore` filter was built once at watcher start and never refreshed. The fs-watch callback now flags ignore-file changes on a shared, swappable filter and the runtime thread rebuilds it between ticks (the tree walk never runs in the callback). Paired renames are also actionable now: `RenameMode::From/To/Both` map to delete + create events instead of a single ambiguous `Renamed` record for a path that may no longer exist.
- IPC hygiene fixes: an oversized frame is answered with the contract's `PayloadTooLarge` error (declared size included) before the session closes, instead of a bare disconnect; EOF in the middle of a length prefix or payload is now a protocol error distinguishable from a clean close at a frame boundary; the socket's parent directory is created `0o700` *before* the socket exists, closing the bind-then-chmod permission window; and the daemon bounds IPC service at `MAX_CONCURRENT_CONNECTIONS` (32) with a `CONNECTION_IDLE_TIMEOUT_MILLIS` (5 min) idle reaper so silent local clients cannot park daemon threads forever.
- `VAPOR_DIR=~/path` now resolves against the home directory on the Rust side (matching the Swift app's tilde expansion) instead of producing a literal `./~/path` directory in no-shell contexts like launchd. An explicitly empty `VAPOR_LOCAL_SYNC_DIRECTORY` now falls back to the configured/default value like the cloud variable always did, instead of silently idling the daemon. `vapor-lifecycle`'s `vapor.json` store was rewritten on `serde_json` (same serializer as the CLI): the hand-rolled parser could match `"autoLaunch"` inside string values of unrelated keys and would rewrite a corrupt file; corrupt JSON is now a hard error that preserves the file.

### Changed

- The runtime loop is event-nudged and adaptive instead of a fixed 4 Hz poll. Fs-event callbacks and IPC control requests signal a new `TickWaker`, so reaction to work is immediate; a fully idle daemon (no pending events, no in-flight work) relaxes to a 1 s tick (`IDLE_TICK_MILLIS`), quartering idle wakeups for the invisible-first / battery goal. ### Fixed

- A deep `VAPOR_DIR` no longer silently costs the daemon its IPC endpoint. `sockaddr_un` caps socket paths at 104 bytes on macOS/BSD (108 on Linux); past it, `bind()` failed and the daemon degraded to running without IPC while `vapor status` claimed it was not running — one WARNING in a log nobody was reading (the new e2e harness caught it on its first sandbox run). Daemon and CLI now share `runtime_paths::ipc_socket_location`: when `<vapor_dir>/vapord.sock` exceeds the shared budget (`constants::ipc::MAX_SOCKET_PATH_BYTES`, 100 bytes) both sides deterministically rendezvous at `<os-temp>/vapor-<fnv1a64(vapor_dir)>/vapord.sock` — same `vapor_dir` → same socket in every process (FNV-1a by hand, since `DefaultHasher` is not stable across separately compiled binaries), distinct `vapor_dir`s cannot collide. The daemon logs the relocation at INFO, refuses a symlinked socket parent (the relocated dir lives under a potentially shared temp root; created `0o700` first), and a new `vapor doctor` probe (`ipc_socket_path`) reports canonical vs relocated placement — Warning when relocated, Failure only if even the relocated path cannot fit. Covered by resolver boundary/determinism unit tests, doctor probe tests, and e2e scenario S9 (deep-`VAPOR_DIR` daemon reachable over the relocated socket, doctor explains it, temp residue cleaned). `docs/architecture/macos/ipc-transport.md` documents the relocation contract.

- `vapor auth login` no longer silently loses every token. `NativeSecretStore` is still backed by the process-local in-memory store on every OS pre-Wave-5 (the Keychain / libsecret / Credential Manager bridges are part of the deferred C4-5 / Wave 12 / Wave 13 work) but the CLI was reporting `auth login: stored token for {provider}` regardless. The token vanished at process exit and the user had no signal that anything was wrong. `core/platform::SecretStore` now exposes an `is_persistent() -> bool` method (default `false`; the trait fakes / Native pre-bridge return `false`, the future Keychain / libsecret / Credential Manager bridges will return `true`); `vapor auth login` emits a stderr warning and tags the success line with `(process-local only)` when the store is non-persistent. `vapor auth status` prepends a matching note in the same case.

- The IPC client now bounds every call with a deadline so a wedged daemon (accepting connections but not answering) cannot hang the CLI. `core/ipc/src/client.rs` exposes `Client::connect_with_timeout` and a `DEFAULT_CALL_TIMEOUT` of 3 s; `Client::connect` applies it to both reads and writes via `set_read_timeout` / `set_write_timeout` after `connect_to_socket`. The CLI maps the resulting `WouldBlock` / `TimedOut` errors onto a new `IpcCliError::DaemonUnresponsive` variant rendered as `vapor: daemon is not responding — check \`vapor logs\``, distinct from the existing `DaemonNotRunning` path which fires when the OS rejects the connect outright. New regression test (`connect_with_timeout_returns_promptly_against_wedged_peer`) binds a UDS, lets the listener accept, holds the stream silent, and asserts `Client::connect_with_timeout` returns inside the L3-7 1 s budget.

- The IPC daemon socket is now created with `0o600` (owner-only) permissions on Unix. `bind_listener` previously left the socket at the umask default, so on a multi-user host any local user could connect to `<vapor_dir>/vapord.sock` and issue control commands (pause / resume / reconcile). `core/ipc/src/transport.rs::unix_impl::bind_listener` now calls `fs::set_permissions` immediately after `UnixListener::bind` using `vapor_shared::constants::runtime::PRIVATE_FILE_MODE`. New regression test asserts the post-bind mode is exactly `0o600`. Also drops the dead `into_inner` method whose comment admitted the implementation was confused.

- IPC transport documentation now agrees with the implementation. `docs/architecture/macos/ipc-transport.md` previously claimed "32-bit big-endian length header" while `core/ipc/src/framing.rs` uses little-endian; the doc now matches the code (and the new Windows / Linux per-OS docs say the same so the codec stays one shared codec across every transport). Adds the missing `docs/architecture/windows/ipc-transport.md` (named pipe at `\\.\pipe\vapord-<user-sid>`, security descriptor, framing, shutdown semantics) and `docs/architecture/linux/ipc-transport.md` (UDS at `<vapor_dir>/vapord.sock`, framing, shutdown), each with the per-OS group `README.md` required by AGENTS.md §10. The transport-agnostic contract in `docs/architecture/ipc-contracts.md` already referenced both files; the dangling links are now resolved.

- `vapor service status` now reports the reverse-DNS service label (`sh.arn.vapor.daemon`) instead of the daemon log filename (`vapord.logs`). The previous report stamp pulled `runtime::DAEMON_LOG_FILE_NAME` for the label field, which was wrong on its face. Centralizes the label in a new `core/shared::constants::service::DAEMON_LABEL` (mirroring `VaporConstants.Daemon.launchAgentLabel` per AGENTS.md §8.6); `core/cli/src/commands/{service,doctor}.rs` consume the constant directly so the LaunchAgent plist filename, the install-time descriptor, the doctor probe, and the status report all agree on one identifier. Regression test in `service.rs` asserts `report.label == DAEMON_LABEL`.

The IPC service's status snapshot was previously written only at startup; the runtime never published updates, so pause / resume / throttle transitions were invisible to every client. `core/daemon::ipc_service` now defines a `StatusPublisher` trait that `DaemonRuntime` calls at the end of every tick (and once on attach), and `core/daemon/src/main.rs` wires the IPC service in via the new `attach_status_publisher` hook. ### Fixed

- `scripts/tests/version.sh` no longer crashes when invoked from inside a parent `git` operation (e.g. the project's `pre-commit` hook). The test now `unset`s `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`, and `GIT_PREFIX` at the top so its `mktemp -d` + `git init` fixture repos resolve cleanly. Without this, git inherited `GIT_DIR` from the hook's environment, "re-init"ed the parent repo instead of the temp dir, and re-fired the pre-commit hook from inside the test fixture — failing every commit that ran under `scripts/hooks.sh`.
- Packaged `Vapor.app` builds now include the SwiftPM localization resource bundle and no longer crash on launch while the app shell resolves UI copy catalogs.
- Packaging now fails fast if either bundled executable is missing, and runtime daemon resolution stays pinned to the bundled `Contents/MacOS/vapord` sibling binary.
- GitHub Actions macOS workflows now run on `macos-26`, matching Vapor's macOS 26-only app target so SwiftUI app tests load against a supported runtime.
- Daemon runtime no longer creates duplicate durable rows each tick when a reconcile fails to start under non-`IdleDrain` throttle; the upserted scheduler intent is now discarded on failed start so the next flush skips it.
- Startup reconstruction barrier now auto-clears after a bounded deadline so non-reconcile work cannot starve indefinitely if the startup reconcile keeps deferring under persistent non-`IdleDrain` pressure.
- Durable intent `attempt_count` now tracks real retry count instead of lease count: `lease_ready_batch` no longer bumps it, `schedule_retry` is the only increment site, and retry caps are enforced at write time so intents cannot reach `MAX_ATTEMPT_COUNT` from throttle-delayed re-leases.
- Durable state `system_time_to_millis` now validates `u128 → i64` conversion symmetrically with the read-path range check, eliminating silent truncation for far-future wall-clock timestamps.
- Durable lease recovery now resets `attempt_count` for leases older than `LEASE_TIMEOUT_MILLIS` (15 minutes) so stale crash-recovered leases don't carry forward inflated retry counts.
- Runtime paths now create private directories and files with restrictive modes at creation time via `DirBuilder::mode` (Rust) and `createDirectory/createFile attributes:` (Swift), including every intermediate directory under the vapor root; the previous two-step create-then-chmod pattern left intermediates at umask defaults and opened a TOCTOU window where the SQLite DB and `vapor.json` were briefly world-readable.
- Log redaction now covers the expanded auth/secret shape set across both daemon and app loggers, matching inline markers for `access_token=`, `refresh_token=`, `api_key=`, `X-Api-Key:`, `client_secret=`, `set-cookie:`, `id_token=`, `session=`, `password=`, and structured metadata keys containing `api_key`, `client_secret`, `refresh`, `oauth`, or `session`.
- FSEvents callback now performs only lexical path normalization and watch-root prefix check; per-component symlink resolution (previously up to 32 `stat`+`readlink` syscalls per event) has moved to the runtime thread, where stabilized events are validated against the real filesystem before entering the scheduler. Events that resolve outside the watch root are dropped with a diagnostic. This restores callback hot-path discipline per AGENTS §3.
- Daemon timing checks no longer stall or silently bypass budgets on wall-clock rewind: the debounce tick now wakes immediately when `duration_since` fails, the reconcile checkpoint treats an impossible-duration as slice-budget-expired, the throttle sampler re-samples on the next tick, and the staged executor advances stages that cannot be measured. Each path has a regression test that walks the clock backwards and asserts the conservative behavior.
- App shell no longer silently rewrites the user-selected `languageCode` to the fallback catalog language on startup. The user's choice is preserved in `vapor.json` across app restarts; the resolved catalog language is surfaced separately as `effectiveLanguageCode` and drives UI strings, so setting an unavailable locale cleanly degrades to English for display without clobbering the persisted preference.
- Swift logger now caches a per-instance `FileHandle`, calls `synchronize()` after every write, and reopens on error instead of opening a fresh handle per log line; heavy-log paths no longer churn thousands of `open()`/`close()` syscalls and crash-time log loss is bounded by the fsync cadence.
- Daemon workgate permit releases no longer silently leak active counts when a stale or mismatched permit is returned: reconcile pause and completion paths now log a diagnostic if `ThrottleWorkgate::release` rejects the permit, surfacing the accounting discrepancy instead of swallowing it.
- Daemon debounce classifier no longer hardcodes `".vaporignore"` and `"vapor.json"`; both file names come from `core/shared::constants` so the classifier can never diverge from the runtime-level names for Vapor's own config and ignore files.
- Daemon now installs a SIGTERM/SIGINT handler that flips a shutdown flag checked by `run_forever`, so `launchctl unload`, `launchctl kill TERM`, or Ctrl-C exit the runtime loop at the next tick boundary instead of terminating mid-lease. Lease recovery on next start still reclaims any in-flight work; the graceful exit just avoids abruptly killing the daemon during an in-progress tick.
- Default provider is now an inert `FilesystemStubProvider` instead of `GoogleDriveProvider`, so pre-GA daemon runs do not point at Google Drive by default. The stub exposes `name = "filesystem_stub"` and reports no remote-changes-feed / no server-side-rename capability so any caller that treats it as real will fail closed. Google Drive remains compiled in and Phase 9 will flip the default once its credentials pipeline is ready.
- App status surfaces the new default provider display name (`Filesystem (stub)`) instead of the hardcoded `Google Drive` string in `AppShellState.initial`; callers that construct state with a real provider name still override it.
- Path-filter startup discovery now skips the heaviest default-ignored directories (`node_modules`, `.git`, `target`, `dist`, `build`, `coverage`, and similar) when walking the watch tree for `.gitignore`/`.vaporignore` files. Those subtrees are still covered by `DEFAULT_PRE_IGNORE_RULES`, so filtering correctness is unchanged, but a fresh start on a tree with millions of `node_modules` files no longer spends minutes enumerating it before the watcher boots.
- LaunchAgent plist writer now emits `StandardOutPath`, `StandardErrorPath`, and `ProcessType = Background` per `docs/operations/launchagent-policy.md`; `AppShellViewModel` wires the stdout/stderr paths under `<vapor_dir>/logs/` so daemon stdout and stderr survive restarts in the expected location.
- `CrashLoopPolicy` defaults and semantics now match the new policy doc: `failureWindow = 600s`, `baseDelay = 2s`, `maxDelay = 120s`, `delayStartsAfterFailures = 1`, plus a new `maxConsecutiveFailuresBeforePause = 5` that drives a durable `CrashLoopPaused` state. `DaemonLifecycleManager` now returns a `CrashLoopDecision` enum (`noDelay` / `backoff(seconds)` / `paused`), exposes `isInCrashLoopPause` and `acknowledgeCrashLoopPause`, and refuses to start the daemon while paused so runaway crashes do not keep restarting in the background.
- `BoundedFsEventRecorder` now records callback events into a small incoming-events queue behind its own mutex and drains the queue into the bounded event/intent maps only on the runtime thread's next `with_state` / `with_mut_state` call. The FSEvents callback no longer contends with the runtime drain's map mutex; the incoming queue is bounded by `MAX_IN_MEMORY_PENDING_PATHS` and drops with a counter rather than growing without limit under a stalled consumer.
